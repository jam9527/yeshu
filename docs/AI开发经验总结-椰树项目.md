## 一、项目概览

### 1.1 项目是什么

椰树集团参观预约小程序 — 一个面向游客和运营团队的微信小程序全栈系统。游客可以在线预约参观（个人/团队），现场扫码核销；运营团队通过管理后台配置预约规则、审核团队预约、查看统计数据；还有推广裂变系统支持分享拉新。

### 1.2 从哪里来

客户提供了一份 **Word 需求文档**（`项目需求.docx`）和一份 **Excel 功能清单**（`椰树集团参观预约小程序.xlsx`），覆盖了小程序端、管理后台、核销、推广四个维度大约 50+ 个功能点。

### 1.3 技术全景

| 维度 | 数据 |
|------|------|
| 项目周期 | 7 周（2026.05.14 → 2026.07.02） |
| 总提交数 | 42 commits |
| 代码规模 | ~31,500 行，281 个源文件 |
| 后端源文件 | 103 个 `.ts` 文件，~6,600 行 |
| 管理后台源文件 | 34 个 `.vue/.ts` 文件，~7,800 行 |
| 小程序源文件 | 69 个 `.ts/.wxml/.scss` 文件，~11,200 行 |
| 后端模块 | 17 个 NestJS 模块，60+ API 端点 |
| 小程序页面 | 19 个页面 |
| 管理后台 | 10 个视图模块，25+ 页面 |
| 数据库表 | 25 张业务表 |

**三层架构**:
```
微信小程序 (原生 TS + Sass)  →  NestJS API (:3000)  →  MySQL 8.4
Vue3 管理后台 (:5173)         →  同一 NestJS API    →  Redis / COS
```

## 二、开发全流程复盘（按阶段）

以下是按时间线梳理的完整开发过程，每个阶段记录了：需求背景 → 我是怎么跟 AI 说的 → AI 做了什么 → 遇到了什么问题 → 怎么解决的 → 可复用的经验。

### Phase 1: 项目初始化与基础设施

**时间**: 2026.05.14 — 05.15 | **提交**: Initial commit, P0/P1/P2 全量修复

#### 需求背景

从零搭建整个项目骨架：
- NestJS 后端（连接 MySQL，JWT 认证，模块化架构）
- Vue 3 管理后台（Element Plus，路由，登录页）
- 微信小程序（TypeScript + Sass，基础页面框架）

#### 我是怎么跟 AI 说的

**第一轮 — 搭后端骨架**:
> "我要做一个微信小程序预约系统，后端用 NestJS + TypeORM + MySQL。请帮我：
> 1. 初始化 NestJS 项目
> 2. 配置 TypeORM 连接本地 MySQL（命名管道 `\\.\pipe\MySQL`）
> 3. 创建 User 和 Reservation 两个核心 Entity
> 4. 实现 JWT 认证模块
> 5. 建立模块化的目录结构"

**第二轮 — 搭管理后台骨架**:
> "用 Vue3 + Element Plus + Vite 创建一个管理后台项目。需要：
> 1. 登录页面（用户名+密码）
> 2. 路由守卫（未登录跳转登录页）
> 3. 侧边栏布局 + 顶部导航
> 4. Axios 封装（baseURL + 拦截器 + token 注入）"

**第三轮 — 搭小程序骨架**:
> "创建微信小程序项目，使用 TypeScript。需要：
> 1. app.ts 全局配置
> 2. 首页、个人中心、预约页面框架
> 3. API 请求工具（基于 wx.request 封装）
> 4. 登录流程页面"

#### AI 做了什么

- 生成了完整的 NestJS 项目（package.json, tsconfig, 模块结构）
- 创建了 TypeORM 实体和数据库配置
- 实现了 JWT 策略和全局守卫
- 创建了 Vue3 项目（Vite 配置、路由、布局组件、登录逻辑）
- 生成了小程序页面骨架和工具函数

#### 遇到的问题

**问题 1**: MySQL 8.4 Windows 版默认禁用 TCP，只能通过命名管道连接。AI 默认生成的是 TCP 连接配置，连不上数据库。

**解决**: 告诉 AI "MySQL 使用 Windows 命名管道 `\\.\pipe\MySQL`，不用 TCP"，AI 更新了 TypeORM 配置。

**问题 2**: 管理后台登录后 token 存储方案不确定。

**解决**: 让 AI 对比了 localStorage vs sessionStorage vs cookie，最终选 localStorage + Axios 拦截器自动注入。

#### 可复用的经验

- 🎯 **"搭骨架"阶段不需要完美，需要快**。这个阶段的目标是三个项目能跑起来、能通信，细节后面再打磨。
- 🎯 **数据库连接是最容易出问题的地方**，先把连接跑通再写业务代码。
- 🎯 **初始化提示词要包含**: 技术栈、目录结构期望、关键配置（如数据库连接方式）。

### Phase 2: 核心业务 + 权限系统

**时间**: 2026.05.15 — 05.16 | **提交**: 角色权限系统、前端修复、Redis/Bull 集成

#### 需求背景

这是项目的核心——预约系统的完整业务逻辑：
- 个人预约（1-5人，选日期/场次，填参观人信息）
- 团队预约（≥10人，提交审核，上传附件）
- 核销流程（扫码 → 确认 → 状态变更）
- 管理后台 RBAC 权限（超级管理员 / 角色权限 / 无角色）

#### 我是怎么跟 AI 说的

**预约模块**:
> "实现个人预约和团队预约功能。需求：
> 1. 每个日期有上午/下午两个场次，每个场次有独立配额
> 2. 个人预约：选日期 → 选场次 → 填参观人（1-5人，姓名+身份证号）→ 确认提交
> 3. 团队预约：选日期 → 选场次 → 填团队信息（≥10人，Excel名单）→ 上传材料 → 提交审核
> 4. 后端需要：配额检查、乐观锁防超卖、状态流转
> 5. 数据库表设计要先给我看"

**权限系统**:
> "实现管理后台 RBAC 权限系统:
> 1. 三个层级: 超级管理员(全部权限) → 角色权限(reservation:review, user:manage, content:manage 等) → 无角色(仅查看)
> 2. 用 NestJS Guard 实现，作为全局守卫
> 3. 支持 @Public() 装饰器跳过认证，@AdminPermissions() 装饰器指定所需权限
> 4. 权限 JSON 存储在 AdminRole 表的 permissions 字段"

#### AI 做了什么

- 设计了 25 张数据库表（预约、配额、核销、用户、权限等）
- 实现了预约 CRUD + 配额检查 + 乐观锁
- 实现了团队预约审核流程
- 实现了核销码生成和扫码核销
- 实现了全局 JwtAuthGuard → RolesGuard 的责任链
- 创建了操作日志拦截器

#### 遇到的问题

**问题 1**: 第一次让 AI 设计的表结构缺少"配额"独立表，配额信息耦合在日期表里，导致后续扩展困难。

**解决**: 明确提出"配额需要独立表，字段包含 version 做乐观锁"，AI 重新设计。

**问题 2**: 全局 Guard 的注册顺序错误——RolesGuard 在 JwtAuthGuard 之前执行，导致 @Public() 装饰器失效。

**解决**: 告诉 AI "JwtAuthGuard 必须在 RolesGuard 之前"，AI 调整了 APP_GUARD 的顺序。

#### 可复用的经验

- 🎯 **数据库设计一定要人 review**。AI 能设计出功能正确的表结构，但"好不好扩展"需要人的经验判断。
- 🎯 **权限系统先画流程图再写代码**。让 AI 先画出"请求 → JWT验证 → 角色查库 → 权限匹配"的数据流，确认后再实现。
- 🎯 **"乐观锁"等专业概念要明确指明**。AI 不会主动加 version 字段防并发，需要人告诉它。

### Phase 3: 登录流程 + DIY 首页

**时间**: 2026.05.17 — 05.18 | **提交**: 登录、隐私协议、DIY组件、WXML折叠修复

#### 需求背景

- 微信小程序登录流程（wx.login → 获取 openid → 手机号授权）
- 登录按钮必须包含隐私协议声明（微信基础库 2.32.3+ 强制要求）
- DIY 首页装修系统（管理后台拖拽式配置首页组件：轮播图、导航、空白间距、展厅列表等）
- 小程序端渲染 DIY 配置的组件

#### 我是怎么跟 AI 说的

**登录流程**:
> "微信小程序登录流程：
> 1. 用户点击'微信一键登录' → wx.login 获取 code → 后端用 code 换 openid
> 2. 同时调用 wx.getPhoneNumber 获取手机号（新版 code 方式）
> 3. 后端 wechat.service.ts: login(code, phoneCode) → 查找或创建用户 → 生成 JWT
> 4. 前端保存 token，后续请求携带
> 5. 登录按钮需要包含隐私协议声明（微信要求）
> 注意：老用户可能用旧的 encryptedData 方式获取手机号，需要兼容"

**DIY 首页**:
> "实现 DIY 首页装修系统：
> 1. 后端: diy-page 模块，pageData JSON 字段存储组件配置
> 2. 组件类型: swiper(轮播图), nav(功能导航), spacer(空白间距), exhibitionList(展厅列表), richText(富文本)
> 3. 管理后台: DIY 页面编辑器，左侧组件库拖拽到右侧预览区，可调整顺序
> 4. 小程序: 根据 pageData JSON 动态渲染组件"

#### AI 做了什么

- 实现了完整的微信登录链路（code → openid → JWT）
- 登录页增加了隐私协议声明组件
- 后端 DIY 模块的 CRUD + 发布机制
- 管理后台的可拖拽编辑器
- 小程序端的动态组件渲染

#### 遇到的问题（这是整个项目中最折磨人的 Bug）

**WXML 压缩问题 — 三次迭代才解决**:

第一版：空白间距组件用 `<view style="height: 40rpx"></view>` → 手机端不生效。
第二版：改为 `padding-top` → 当空白间距是首页第一个组件时，被微信渲染器完全折叠。
第三版：在里面放 `<text> </text>` → 微信压缩空格。
最终版：`<text decode="{{true}}">&nbsp;</text>` + 首组件特殊处理（把高度移到容器 padding-top）。

**关键教训**: 微信小程序的渲染引擎有自己的"优化"逻辑——它会压缩空白节点。这类平台特有行为，AI 不可能提前知道，只能人真机测试→反馈症状→AI 提方案→再测试。

#### 可复用的经验

- 🎯 **微信小程序开发 = AI 写代码 + 人真机验证**。这是铁律，很多问题在模拟器上不出现。
- 🎯 **平台特有 Bug 用"试错循环"解决**: 人描述现象 → AI 提候选方案 → 人验证 → 反馈结果 → AI 调整。
- 🎯 **DIY/配置化系统的接口设计**: JSON 配置结构要在前后端之间明确定义，这是最容易出现不一致的地方。

### Phase 4: 推广追踪 + 分享 + 域名迁移

**时间**: 2026.05.22 — 05.23 | **提交**: 6 个 fix/feat，是提交最密集的阶段

#### 需求背景

这是项目中最复杂的业务链路——推广裂变系统：
- 推广员分享小程序链接，携带 promoterId 参数
- 新用户通过链接进入 → 记录"点击"
- 用户登录 → 绑定推广关系
- 用户完成预约 → 关联推广记录
- 核销完成 → 标记推广核销
- 推广员查看漏斗数据（访问数 / 注册数 / 预约数 / 核销数）

还有两个附加任务：域名从 `yeshu.weicent.cn` 迁移到 `yuyue.yeshu.com`，以及解决分享按钮灰色的问题。

#### 我是怎么跟 AI 说的

**第一轮（失败）**:
> "实现推广追踪功能：用户通过分享链接进入小程序，记录推广关系，统计推广效果。"

**问题**: 描述太模糊，AI 只做了基本的数据表和后端 API，没有考虑到前端链路中的关键时机。

**第二轮（修复）**:
> "推广统计全部为 0。我梳理了完整的数据流，请按照以下时序修复:
>
> 1. 用户点击分享链接进入小程序 → app.ts onLaunch 捕获 promoterId 存到 globalData
> 2. 用户点击登录 → 后端 wechat.service.ts login() 方法中:
>    a. 先记录 promotion_click（不管用户是否已存在）
>    b. 如果是新用户，设置 user.promotedBy = promoterId
> 3. 用户完成预约 → reservation.service.ts create() 方法中:
>    a. 查询 user.promotedBy
>    b. 在 promotion_record 中创建或更新记录（linkReservation）
> 4. 核销完成 → verification.service.ts confirm() 方法中:
>    a. 查询该预约是否有关联的推广记录
>    b. 更新 markVerified
> 5. 统计 API /promotion/stats 从 promotion_record 表计数
>
> 特别注意:
> - handlePhoneLogin 中只有登录成功后才清除 promoterId（之前是调用 API 前就清除了，导致失败回退时 promoterId 丢失）
> - 已登录用户点击分享链接也需要调用 /promotion/click API"

**分享功能**:
> "所有小程序页面（除登录页和个人信息页）需要支持分享功能：
> 1. app.ts Page 拦截器中自动注入 onShareAppMessage，携带 promoterId
> 2. onShow 中调用 wx.showShareMenu 启用分享按钮
> 3. tab 页用 wx.reLaunch 代替 wx.switchTab（后者不支持携带参数）"

**域名迁移**:
> "把所有代码中的 yeshu.weicent.cn 替换为 yuyue.yeshu.com。注意：
> 1. config.ts 中的 PROD_URL
> 2. 微信公众平台回调地址
> 3. Nginx 配置
> 4. SSL 证书（Let's Encrypt）"

#### AI 做了什么

- 根据详细的时序描述，重新实现了完整的推广追踪链路
- 实现了全局分享拦截器
- 替换了所有域名引用
- 修复了 getPhoneNumber API 的新旧兼容

#### 遇到的问题

**问题 1**: 推广追踪第一次实现全部为 0——这就是"模糊需求"的代价。根因是前端 `handlePhoneLogin` 在调用 API 前就清除了 `promoterId`，登录失败回退到 `handleCodeLogin` 时 promoterId 已丢失。

**问题 2**: 域名迁移时遗漏了 `wechat.service.ts` 中的回调地址。因为 AI 只搜索了 `yeshu.weicent.cn` 字符串，而那个回调地址是拼接的。

**问题 3**: `wx.switchTab` 不支持携带参数，导致从分享链接进入后跳转 tab 页时 promoterId 丢失。

#### 可复用的经验

- 🎯 **复杂业务链路的提示词 = 数据流时序图 + 每个节点的操作 + 边界情况**。这是本项目最重要的经验。
- 🎯 **跨文件全局变更，人必须做最终的 grep 验证**。不要完全信任 AI 的搜索替换。
- 🎯 **微信 API 的坑（如 switchTab 不传参）需要主动告诉 AI**，否则 AI 会按常规思路实现。

### Phase 5: 内容增强 + 富文本 + 日历

**时间**: 2026.06.07 — 06.08 | **提交**: 富文本编辑器修复、日历修复、预约次数限制

#### 需求背景

- 展厅/活动的内容编辑器需要支持富文本（图片、视频、格式化文本）
- 日历组件默认显示当前月份（之前固定在某个月）
- 预约次数限制（每人每天/每周/每月限制）
- 定时任务自动 seed 预约限制数据

#### 我是怎么跟 AI 说的

**富文本**:
> "管理后台的展厅/活动编辑需要使用富文本编辑器。请集成 wangEditor（或推荐其他适合 Vue3 的富文本编辑器）。要求：支持图片上传、视频插入、文字格式化。编辑器样式需要适配 Element Plus 风格。"

**日历修复**:
> "小程序预约页面的日历有两个问题：
> 1. 默认显示的不是当前月份
> 2. 过去的日期应该显示为灰色不可选，但现在有些过去日期可以点击
> 修复: 1) 初始化时用 new Date() 获取当前年月 2) 渲染时判断日期是否在今天之前"

#### AI 做了什么

- 集成了富文本编辑器（选择了适合 Vue3 的方案）
- 修复了日历组件逻辑
- 实现了预约频率限制的后端校验
- 添加了定时任务自动 seed 数据

#### 遇到的问题

**问题 1**: 富文本编辑器生成的 HTML 内容过大，保存时出现 Network Error。原因：NestJS 默认 body-parser 限制 100KB。

**解决**: 在 `main.ts` 中设置 `app.use(bodyParser.json({ limit: '10mb' }))`。

**问题 2**: 日历组件中"过去日期判断"只比较了日期数字，没有比较月份和年份。

**解决**: 让 AI 用 `new Date(year, month, day) < new Date(today)` 做完整日期比较。

#### 可复用的经验

- 🎯 **富文本编辑器选型让 AI 推荐并给出理由**，它会比较多个方案。
- 🎯 **body-parser 限制是 NestJS 的经典坑**，遇到 Network Error 但后端没报错时优先排查这个。
- 🎯 **日期比较永远用 Date 对象**，不要手动拆数字比较。

- 描述症状（不是结论）

- 先让 AI 分析根因
- 确认根因后再修

**效果**: 通常需要 2-3 轮，AI 给方案 → 验证 → 反馈 → 调整。

**关键要素**:
- 提供当前代码
- 描述"什么环境正常、什么环境不正常"

## 八、改进与优化建议

### 8.1 流程层面

| 问题 | 改进方案 | 优先级 |
|------|----------|--------|
| 需求描述不够精确导致返工 | 使用「Prompt 模板 3」描述复杂链路，包含时序和每个节点的操作 | 🔴 高 |
| AI 修改后验证不充分 | 每个模块建立 checklist：正常路径 + 边界 + 错误处理，人逐条验证 | 🔴 高 |
| 跨模块变更容易遗漏 | 建立"影响范围检查"流程：grep → 列出引用 → 逐个确认 → 人最终验证 | 🔴 高 |
| Memory 维护不及时 | 每个 session 结束前预留 5 分钟写 Memory | 🟡 中 |
| 一次提太多需求 | 每个 session 聚焦 1-2 个模块，完成后验证再继续 | 🟡 中 |

### 8.2 技术层面

| 问题 | 改进方案 | 优先级 |
|------|----------|--------|
| 缺少自动化测试 | 对核心链路（预约、核销、推广）补充 e2e 测试 | 🔴 高 |
| TypeScript 编译链路不清晰 | 统一构建脚本，pre-commit hook 强制编译检查 | 🟡 中 |
| 日志和监控不足 | 结构化日志 + 关键业务指标监控 | 🟡 中 |
| 环境差异导致问题 | docker-compose 统一开发环境 | 🟢 低 |

### 8.3 AI 使用技巧 Top 10

1. **"先跑通再完善"**: 让 AI 先写最小可行版本，验证通过后再迭代，减少浪费
2. **"先梳理再编码"**: 复杂业务先让 AI 列出数据流，确认后再写代码
3. **"参照 XXX 做 YYY"**: AI 的模式复用能力很强，利用已完成的模块做模板
4. **Bug 先说症状**: 不要直接告诉 AI "改哪里"，让它做根因分析
5. **跨模块变更先 grep**: 人做全局搜索确认所有引用点，再让 AI 逐个修改
6. **"生产环境需要注意什么"**: 每个模块完成后追问这句，暴露隐藏配置问题
7. **定期 Code Review**: 用 `/code-review` 命令让 AI 审查 AI 写的代码
8. **"只做 XXX，不要扩展"**: 明确限制范围，防止 AI 过度实现
9. **复杂逻辑分段提问**: 不要一次描述整个系统，分模块逐步推进
10. **善用 Plan Mode**: 大功能先出计划再编码，避免方向性错误

## 九、下次新项目的启动清单

当开始一个新项目时，按以下顺序操作：

### Step 1: 复制 CLAUDE.md 模板
```bash
cp ~/.claude/projects/D--work-CC-yeshu/memory/claude-md-template.md ./CLAUDE.md
```
然后根据新项目修改下半部分（项目信息）。

### Step 2: 建立项目 Memory
在新项目的 Memory 目录下创建：
- `project-overview.md` — 项目概述
- `user-profile.md` — 已有，无需修改
- `progress-status.md` — 进度跟踪

### Step 3: 初始化项目骨架（让 AI 做）
```
"初始化 [项目名] 项目。技术栈: [前端框架] + [后端框架] + [数据库]。
请创建: 1) 后端项目骨架 2) 前端项目骨架 3) 数据库连接配置
关键配置: [数据库连接方式、端口、特殊约束]"
```

### Step 4: 第一个业务模块（验证全链路）
选择一个简单的 CRUD 模块（如"内容管理"），从后端 → 管理后台 → 小程序/前端完整跑通，验证全链路正常后再铺开。

### Step 5: 逐步推进
- 核心业务模块（用分步确认模式）
- 权限/认证系统
- 第三方平台对接（微信/支付宝/支付）
- 性能和优化
- 文档和验收

### Step 6: 收尾
- 让 AI 扫描所有 TODO/FIXME
- 生成验收清单
- 让 AI 补充错误处理
- 部署文档

## 十一、人机分工总结

### AI 擅长（放心交给 AI）
- ✅ 标准 CRUD 代码生成（Entity → Service → Controller → 页面）
- ✅ 技术文档编写（架构、API、数据库、部署）
- ✅ 代码模式复用（"参照 A 做 B"）
- ✅ 带标准答案的性能优化（连接池、集群、限流）
- ✅ Bug 根因分析（基于你提供的症状和日志）
- ✅ 代码审查（发现潜在问题）
- ✅ 错误处理的补充

### 人必须做（AI 无法替代）
- 🔑 需求理解和优先级判断
- 🔑 业务逻辑的最终确认
- 🔑 安全策略和合规审查
- 🔑 微信真机验证（模拟器和真机行为不一致）
- 🔑 部署和运维（SSH、Nginx、SSL）
- 🔑 微信公众平台配置（域名白名单、业务域名）
- 🔑 客户沟通和需求对齐
- 🔑 数据库设计的扩展性判断

### 人机协作的最佳模式

| 场景 | 分工 |
|------|------|
| 复杂 Bug | 人: 描述症状 + 排查信息 → AI: 根因分析 → 人: 验证修复 |
| 架构设计 | 人: 提需求 → AI: 多个方案对比 → 人: 做最终决策 |
| 代码 Review | AI: 第一遍扫描 → 人: 最终判断 |
| 文档 | AI: 生成初稿 → 人: 补充业务背景和注意事项 |
| 新模块 | 人: 描述需求+字段+API → AI: 生成代码 → 人: review+测试 |
| 性能优化 | 人: 描述瓶颈 → AI: 系统性方案 → 人: 选择优先级 |

### 一句话总结

> **AI 是超级高效的"高级工程师"，但项目管理、架构决策、业务理解、质量把控和客户沟通，仍然需要人来主导。最好的模式不是"AI 替人干活"，而是"人告诉 AI 做什么、检查 AI 做得好不好、决定什么时候算完成"。**
